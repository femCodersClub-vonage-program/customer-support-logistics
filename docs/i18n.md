# Internationalisation (i18n)

Every user-facing text comes from translation files, in the language of the person who reads or hears it. Spanish (`es`) is the default and fallback; English (`en`) is the second language. Why we chose these libraries is in [ADR 0006](adr/0006-internationalisation.md).

## Where things live

| Place                                  | What it holds                                                                                            | Library                              |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| `packages/shared-types/src/locale.ts`  | `SUPPORTED_LOCALES`, `Locale`, `DEFAULT_LOCALE`. `Customer` and `Driver` have a `locale`.                | -                                    |
| `packages/i18n/src/messages/*.json`    | Labels shared by every app: incident statuses and types, order statuses, language names.                 | -                                    |
| `packages/i18n/src/locale.ts`          | `isLocale`, `negotiateLocale` (pick a supported locale from preferred languages), `parseAcceptLanguage`. | -                                    |
| `apps/client/src/i18n/messages/*.json` | Client PWA copy.                                                                                         | `use-intl`                           |
| `apps/crm/src/i18n/messages/*.json`    | CRM copy and metadata.                                                                                   | `next-intl`                          |
| `apps/api/src/i18n/messages/*.json`    | SMS and voice prompts.                                                                                   | `createTranslator` (`use-intl/core`) |

Each app merges the shared labels with its own messages, so `t('incidentStatus.open')` works everywhere.

Enum **values** (`in_mediation`, `wrong_item`…) stay in English in the code and the database. Only their labels are translated.

## How each app picks the language

- **Client:** the choice saved in `localStorage` (`csl:locale`), then `navigator.languages`, then `es`. The language switcher changes it without a reload and keeps `<html lang>` in sync.
- **CRM:** the `NEXT_LOCALE` cookie, then the `Accept-Language` header, then `es`. The switcher calls a Server Action that sets the cookie; Next.js re-renders the current page with the new language.
- **API:** always the `locale` stored on the recipient (`Customer` or `Driver`), never the request.

## Message format

Messages use [ICU MessageFormat](https://formatjs.io/docs/core-concepts/icu-syntax):

```json
{
  "report": { "order": "Pedido {orderId}" },
  "sms": { "callSoon": "Te llamaremos en {minutes, plural, one {# minuto} other {# minutos}}." },
  "install": { "iosShare": "Toca el botón Compartir <icon></icon> en la barra de Safari." }
}
```

- Use variables and plurals. Never build a sentence by concatenating strings in code: word order changes between languages.
- Tags such as `<icon></icon>` are filled with `t.rich(key, { icon: () => <Icon /> })`.
- In ICU, an ASCII apostrophe (`'`) next to `{` or `}` starts a quoted section. Write `’` in screen copy; in SMS use `'`, because `’` is not in GSM-7 (see below).

Keys are typed: a missing or misspelled key, or a missing variable, is a TypeScript error.

## Adding a key

1. Add the key to `messages/es.json` **and** `messages/en.json` of the app (or of `packages/i18n` if more than one app needs it).
2. Use it: `const t = useTranslations('namespace')` in a component, `await getTranslations('namespace')` in an async Server Component of the CRM, or `getTranslator(locale)` in the API.
3. Run the tests of that app or package: a test fails if a key exists in one language and not in the other.

Don't write user-facing text directly in JSX. The `i18next/no-literal-string` lint rule (in `@csl/config/eslint/react-core`) fails on text in JSX and in attributes that people read, such as `alt`, `placeholder` and `aria-label`. The plugin never checks some DOM attributes (`title` among them), so review those by hand.

## Adding a language

1. Add its code to `SUPPORTED_LOCALES` in `packages/shared-types/src/locale.ts` ([BCP 47](https://www.rfc-editor.org/info/bcp47), for example `fr` or `es-MX`).
2. Run `pnpm typecheck`. TypeScript lists every place that needs the new language:
   - a `messages/<code>.json` in `packages/i18n`, `apps/client`, `apps/crm` and `apps/api`, imported in each `messages.ts`;
   - its name in every `localeName` group;
   - its Vonage codes in `apps/api/src/vonage/locales.ts`: the text-to-speech `language` (for example `fr-FR`) and the Verify v2 `locale` (for example `fr-fr`). Check that Vonage supports them.
3. Run the tests: the key comparison and the SMS length tests cover the new files.

## SMS length and encoding

An SMS is sent in GSM-7 when every character is in the GSM 03.38 alphabet, and in UCS-2 otherwise:

| Encoding | One SMS        | Each part of a longer SMS |
| -------- | -------------- | ------------------------- |
| GSM-7    | 160 characters | 153 characters            |
| UCS-2    | 70 characters  | 67 characters             |

GSM-7 includes `ñ`, `Ñ`, `é`, `É`, `ü`, `¿` and `¡`, but **not** `á`, `í`, `ó`, `ú`, `’` or emoji. One of them switches the whole SMS to UCS-2, and it can cost two or three parts instead of one. `€`, `^`, `{`, `}`, `[`, `]`, `~`, `|` and `\` are in GSM-7 but count as two characters.

We keep correct Spanish spelling and write short templates instead. When a word with `á`, `í`, `ó` or `ú` makes a template too long, rephrase it (for example "domicilio" instead of "dirección"). `measureSms` in `apps/api/src/vonage/sms-segments.ts` returns the encoding, length and parts of a text, and `sms-templates.spec.ts` fails if any template, with any incident type and in any language, needs more than one SMS.

Measured with an 8-character order id (`A1B2C3D4`) and, for the incident notice, the longest incident type:

| Template         | Purpose                                           | `es`              | `en`              |
| ---------------- | ------------------------------------------------- | ----------------- | ----------------- |
| `incidentNotice` | Incident details to the driver                    | GSM-7, 130, 1 SMS | GSM-7, 111, 1 SMS |
| `callSoon`       | "We'll call you in 2 minutes"                     | GSM-7, 70, 1 SMS  | GSM-7, 70, 1 SMS  |
| `callFallback`   | The driver didn't answer the call                 | GSM-7, 80, 1 SMS  | GSM-7, 76, 1 SMS  |
| `invalidReply`   | The driver replied something other than 1, 2 or 3 | GSM-7, 23, 1 SMS  | GSM-7, 28, 1 SMS  |

Longer order ids reduce the margin: the Spanish incident notice has 30 characters left. Driver replies stay numeric (`1`, `2`, `3`) in every language, so parsing them doesn't depend on the language.

## Voice and Verify

- The driver's call prompt (`buildDriverPromptNcco` in `apps/api/src/vonage/ncco.ts`) uses the driver's `locale` for the `talk` text and its text-to-speech `language` (`es-ES`, `en-GB`).
- Verify v2 requests send the customer's `locale` mapped with `toVerifyLocale` (`es-es`, `en-gb`), so the code SMS arrives in their language.

## Dates, times and numbers

Format them with the library, never by hand: `useFormatter()` in React components and `getFormatter()` in CRM Server Components. They use `Intl` in the active language. The CRM formats times in `Europe/Madrid` (`TIME_ZONE` in `apps/crm/src/i18n/locale.ts`), so the server and the browser render the same text.

## Tests

Render components with `renderWithIntl(ui, { locale })` from `src/test/render.tsx` in the client and the CRM. It uses `en` by default; add a case in `es` when a component's copy matters.

## Out of scope

Translating free text written by users (incident descriptions, agent notes), translating the mediation call live, right-to-left languages and a translation management platform.
